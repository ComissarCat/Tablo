# Tablo — информационное табло для залов судебных заседаний

## Что это

.NET-решение из трёх проектов, показывающее на экране в зале суда сегодняшние
дела: номер, судью, участников, результат рассмотрения (если уже вынесен).
Заменяет прежнее браузерное решение (проблемы: всплывающие окна поверх
контента при сбое обновления, неудобный масштаб, нестабильность).

Требования, под которые спроектировано:
- вывод по конкретному залу или все дела на день сразу;
- фильтр по видам дел (гражданские/административные/уголовные) в любой
  комбинации;
- настраиваемый масштаб интерфейса;
- работает и на Windows, и на Linux (оба — с обычным рабочим столом);
- периодическое обновление данных (в БД может появиться результат);
- отказоустойчивость — никаких модальных ошибок поверх табло, при сбое
  показываются последние известные данные;
- запуск через автозагрузку/Планировщик заданий, без участия оператора.

## Структура решения

```
Tablo.slnx
src/
  Tablo.Shared/   DTO контракта API (CaseDisplayItem, PartyLine, CaseCategory,
                   CasesResponse, HallInfo) — общие для сервера и клиента
  Tablo.Server/    ASP.NET Core сервис: опрашивает Firebird по таймеру,
                   кэширует в памяти, отдаёт REST (/api/cases, /api/halls,
                   /health). Один инстанс на всю систему (центральная БД
                   доступна по сети из всех зданий/залов)
  Tablo.Client/    Avalonia-приложение — само табло, разворачивается на
                   каждом мониторе/машине в зале
deploy/
  windows/         install-client-autostart.ps1 + run-client-loop.bat
                   (клиент, автозапуск через "Автозагрузку" — основной
                   способ, работает и на Windows 7/Server 2008),
                   register-task.ps1 (клиент, через Планировщик заданий —
                   только Windows 8/Server 2012+), register-server-
                   service.ps1 (сервер как служба Windows)
  linux/           tablo-client.service / tablo-client.desktop (клиент),
                   tablo-server.service (сервер)
```

## Как это работает

- `Tablo.Server` — единственный компонент, который трогает Firebird
  (`FirebirdSql.Data.FirebirdClient`). `CaseDataPollerService` опрашивает БД
  каждые `Tablo:PollIntervalSeconds` секунд (appsettings.json), результат
  кладёт в `CaseDataCache`. Если опрос не удался — кэш **не затирается**,
  отдаются последние известные данные с пометкой `IsStale=true`
  (`GET /api/cases`). Ретраи вокруг запроса к БД — через Polly.
- `Tablo.Client` читает локальный `tablo.config.json` рядом с exe (адрес
  сервера, `HallName` — точное название зала как в `CATALOGCONTENT.NAME`
  (без учёта регистра/пробелов по краям), null/пусто = все залы; актуальный
  список названий смотреть через `GET /api/halls` на сервере, флаги
  `ShowCivil/ShowAdministrative/ShowCriminal`, `UiScale`,
  `PollIntervalSeconds`). Опрашивает `Tablo.Server` по таймеру. При сбое сети
  — не показывает диалогов, оставляет последние данные, в статус-строке внизу
  пишет время последнего обновления (оранжевым, если данные устарели).
  Масштаб — `LayoutTransformControl` (не `RenderTransform`!) вокруг
  заголовка и списка дел, не завязан на DPI/зум ОС. `RenderTransform`
  сначала использовался, но масштабирует только отрисовку, не раскладку —
  при `UiScale > 1` контент вылезал за правый край экрана вместо переноса
  по словам. `LayoutTransformControl` учитывает масштаб уже при измерении,
  поэтому текст корректно переносится в пределах экрана. Статус-строка
  внизу (`StatusText`) специально вынесена НАРУЖУ этого контейнера — не
  масштабируется никогда, по требованию.
  Полноэкранный режим без рамки (`WindowState.FullScreen` +
  `WindowDecorations.None`). Esc закрывает окно (для обслуживания на месте).
  Сверху закреплённый заголовок "Список дел, назначенных к рассмотрению на
  {дата}" (+ "Зал {HallName}", если настроен конкретный зал); в режиме "все
  залы" название зала дублируется на каждой карточке дела, не только в
  заголовке группы — иначе при автопрокрутке длинного списка теряется,
  к какому залу относятся видимые карточки.
  Дела сортируются по времени заседания (`EVENT_TIME`, дела без времени —
  в конец списка); список медленно автопрокручивается, если не помещается
  на экран целиком (пауза 3с у каждого края, затем прыжок наверх) — скорость
  и паузы сейчас захардкожены в `MainWindow.axaml.cs`
  (`ScrollSpeedPxPerSecond`, `ScrollPauseSeconds`), в конфиг не вынесены.
- Автозапуск и перезапуск при падении — задача внешнего watchdog, не
  самого приложения — см. `deploy/README.md`. На Linux — systemd
  `Restart=always`. На Windows — **два варианта**: папка "Автозагрузка" +
  `run-client-loop.bat` (watchdog-цикл на чистом cmd, работает на любой
  версии Windows, в т.ч. 7/Server 2008 — это основной/рекомендуемый способ,
  `install-client-autostart.ps1`) или классический Планировщик заданий
  (`register-task.ps1`, но командлеты `New-ScheduledTaskAction/-Trigger`
  требуют PowerShell 3.0+/Windows 8+/Server 2012+ — на Windows 7 их нет).
  Bat-цикл проверяет код выхода процесса: 0 (штатный Esc) — не
  перезапускает, не 0 (падение) — перезапускает через 3с; эта логика
  завязана на то, что `Program.cs` клиента возвращает 0 при обычном
  закрытии и явно ставит `Environment.ExitCode = 1` только в catch-блоке
  необработанного исключения — не убирать это поведение не проверив bat.

## Источник данных (Firebird 1.5, `uni_work2003.gdb`)

Полная схема БД гораздо больше; ниже — только то, что использует Tablo.
Подробности DDL см. в файле `tablo` (частичный дамп) и `Данные для
вывода.txt` в корне репозитория.

Две параллельные ветки таблиц:
- `G33_*` — **гражданские и административные** дела вместе, различаются по
  `G33_PROCEEDING.CASE_TYPE_ID` (910760002 = гражданское, 910760004 =
  административное).
- `U33_*` — **уголовные** дела, отдельная ветка целиком (колонки
  `CASE_TYPE_ID` там нет).

Зал заседания — на `*_EVENT.ROOM_NUMBER_ID` (не на `*_PROCEEDING`), поэтому
"дела на сегодня" — это выборка от `*_EVENT` по `EVENT_DATE`, присоединённая
к `*_PROCEEDING`. Один `EVENT` = одна строка на табло (если у дела несколько
заседаний за день — несколько строк).

Справочники (полная структура неизвестна, использованы только нужные
столбцы):
- `CATALOGCONTENT.CONTENTID → .NAME` — залы (`*_EVENT.ROOM_NUMBER_ID`), роли
  сторон (`G33_PARTS.PARTS_TYPE_ID`), результаты рассмотрения
  (`G33_PROCEEDING.SATISFIED_VERDICT_I_ID`,
  `U33_PROCEEDING.VERDICT_BY_PROTEST`).
- `GROUPCONTENT.GROUPCONTENTID → .USERNAME` — судья
  (`*_PROCEEDING.JUDGE_SPEAKER_ID`).

Участники процесса:
- Гражд./админ. (`G33_PARTS`): только `PARTS_TYPE_ID` IN (50400000 истец,
  50400001 ответчик, 50400100 административный истец, 50400101
  административный ответчик), сгруппированы по роли.
- Уголовные (`U33_PARTS`): `NAME` + `MAIN_LAW_ARTICLE`, без группировки.

Точные SQL-запросы — `src/Tablo.Server/FirebirdCaseRepository.cs`.

Пошаговая инструкция по развёртыванию сервера и клиента (с нуля и
обновление уже работающих) — `deploy/README.md`.

## Рантайм на целевых машинах

Целевые машины (залы, сервер) без интернета — поэтому и сервер, и клиент
публикуются **self-contained** (`--self-contained true`): .NET-рантайм
целиком упаковывается рядом с exe, отдельно ставить .NET на машине не нужно.
Firebird-клиент тоже не требует установки `fbclient.dll` — это чистый
управляемый провайдер, говорящий по сети напрямую (проверено).

Собрать публикации для Windows и Linux (нужен интернет — но только на
машине сборки, не на целевых): `deploy/publish.ps1` → кладёт результат в
`publish/server-win-x64/`, `publish/client-win-x64/`,
`publish/server-linux-x64/`, `publish/client-linux-x64/`. Дальше эти папки
целиком копируются на целевые машины (флешка/внутренняя сеть) — этого
достаточно, никакой установки рантайма на месте.

## Открытые вопросы / на что смотреть при следующей доработке

- Фильтр зала в клиенте (`HallName`) сравнивается по точному названию
  (`CATALOGCONTENT.NAME`), не по ID. Если в разных зданиях/судах названия
  залов пересекаются (например, несколько "Зал №1" в разных зданиях,
  использующих общий справочник `CATALOGCONTENT`) — табло по имени может
  зацепить не тот зал. Пока с этим не сталкивались; если возникнет —
  вернуть фильтрацию по `HallId` (в API он никуда не делся, есть в каждом
  `CaseDisplayItem`) либо просить называть залы уникально по зданиям.
- Точные типы `CATALOGCONTENT`/`GROUPCONTENT` и домена `TRANSPORTABLE_DATE`
  не подтверждены на реальной БД (в дампе их нет) — сверить при первом
  подключении к боевой/тестовой БД.
- `ConnectionStrings:Firebird` в `src/Tablo.Server/appsettings.json` —
  плейсхолдер, реальные хост/пароль подставляются при разворачивании.
- Список залов (`HallInfo`) больше **не** отдельный SQL-запрос — он строится
  в C# из уже полученных сегодняшних дел (`FirebirdCaseRepository.
  GetTodayCasesAsync`). Раньше был отдельный запрос по `CATALOGCONTENT`,
  проверяющий, на какие зал-`CONTENTID` вообще ссылались события — но
  `*_EVENT.ROOM_NUMBER_ID` не проиндексирован, и без фильтра по дате это был
  полный скан всей многолетней истории заседаний (на боевой БД — минуты),
  что на практике стабильно попадало под плановый перезапуск Firebird
  (обрыв соединения каждые ~30 минут у заказчика) и опрос никогда не
  завершался успехом. Если понадобится справочник залов сам по себе
  (не только те, что встречаются сегодня) — не возвращать старый запрос
  как есть, сначала завести индекс на стороне БД.
- `G33_PARTS.PROC_ID` и `U33_PARTS.PROC_ID` **не проиндексированы** в
  исходной схеме (нет такого индекса в дампе `tablo`, есть только FK-
  ограничение без индекса — Firebird 1.5 не создаёт индекс под FK
  автоматически). Основные запросы дел джойнят эти таблицы по `PROC_ID` —
  пока не создавали проблем на практике, но если `/api/cases` после фикса
  выше всё ещё будет отвечать медленно (много секунд), следующий подозреваемый
  — это. Чинится на стороне БД (нужен админ БД, это боевая система):
  `CREATE INDEX G33_PARTS_PROC_ID ON G33_PARTS (PROC_ID);` и аналогично для
  `U33_PARTS` — сам не делал, это решение не мне принимать без владельца БД.
- Важный нюанс `FirebirdSql.Data.FirebirdClient`: имена кодировок вроде
  `WIN1251` он распознаёт только если в процессе явно зарегистрирован
  `System.Text.Encoding.CodePagesEncodingProvider` (без этого соединение
  падает с `ArgumentException: Invalid character set specified` ещё до
  обращения к сети). Регистрация уже добавлена первой строкой в
  `src/Tablo.Server/Program.cs` — если писать новый код, который открывает
  `FbConnection` отдельно от этого процесса, регистрацию нужно повторить там.
- Конфигурация табло — только локальный файл на каждой машине (осознанное
  решение для первой версии); центральное управление конфигами залов можно
  добавить позже, если залов станет действительно много.
- .NET 8/10 официально поддерживает Windows 10/Server 2012 R2 и новее —
  Windows 7/Server 2008/2008 R2 в список поддерживаемых ОС не входят (это
  одна и та же линейка ядра 6.1). На практике и `Tablo.Server` на
  Server 2008 R2, и `Tablo.Client` на Windows 7 у заказчика запускались и
  работали (ключевая проблема с зависанием опроса БД оказалась не в этом —
  см. фикс `LoadHallsAsync` выше; на Windows 7 споткнулись отдельно о
  PowerShell/Планировщик заданий — см. фикс автозапуска клиента выше), но
  это не гарантия на будущее. Сервер уже сознательно перенесли на
  Server 2012. Если где-то ещё придётся ставить на 7/2008 — иметь в виду
  как источник необъяснимых проблем в первую очередь, и что многие
  современные командлеты PowerShell (ScheduledTasks, NetSecurity/
  `New-NetFirewallRule`, `Test-NetConnection`) там попросту недоступны.
